# 개발 변경 수행

사용자가 제시한 목표·완료 조건·제약 안에서 개발 변경을 수행한다. 이 Skill은 특정 에이전트의 도구 이름·병렬 기능·Hook을 요구하지 않는다.

## 입력과 연결

- 현재 요청과 적용 지침에서 이번 목표·완료 조건·제약을 파악한다. 누락된 정보가 기존 프로젝트에서 확인 가능하면 먼저 확인한다.
- 연결 지침이 지정한 프로젝트 root 기준 `harness/RULES.md`, `AGENTS.md`와 Root `README.md`의 필요한 준비·검증 정보를 읽고 이미 읽었다면 재사용한다. 이것은 Skill 파일 위치나 shell의 현재 디렉터리 기준 상대 경로가 아니다.
- 적용 시 공통 문서 경로를 바꿨으면 해당 연결을 따른다. root·연결 파일이 불명확하면 현재 작업과 관련된 지침만 좁게 확인한다. 필수 규칙·실행 계약을 확인하지 못한 행동은 진행하지 않고, 무관한 프로젝트 전체 탐색으로 대신하지 않는다.
- 승인·사실성·기존 작업 보호·기록의 기준은 공통 규칙과 프로젝트 지침을 따른다. 이 Skill이 추가 권한을 부여하지 않는다.

## 필요한 맥락과 구현

완료 조건에 관계된 Source·Test·Config·문서와 현재 Working Tree만 확인한다. 기존 수정과 이번 작업의 경계를 파악하고, 유효한 기존 관측을 재사용한다. 계획이 유용한 규모라면 작업을 논리적 단위로 나누되 작은 수정에 별도 계획 문서를 만들지 않는다.

기존 구조와 Convention에 맞는 최소 변경을 구현한다. 승인된 계약·요구사항 변경의 직접 영향을 받는 호출부·설정·Test·문서·참조는 함께 일관되게 맞춘다. 완료 조건을 충족하는 데 필요한 경우에만 관련 Test·문서를 보완한다. Scope 밖 문제는 보고하고 함께 수정하지 않는다. 중요한 결정에 사용자 판단이 필요하면 독립 작업을 이어가며 의존하는 변경은 보류한다.

## 검증 선택·실행

변경한 동작과 실패 위험에 맞춰 프로젝트의 기존 검증을 선택한다. 작은 변경은 관련 검증부터 수행하고, 영향이 넓거나 프로젝트 규칙이 요구하면 통합 검증을 포함한다. 현재 변경에도 유효한 검증을 관성적으로 반복하지 않는다. 문서만 바뀌면 링크·명령·내용의 정확성을 확인하고 기능 검증은 필요한 경우에만 실행한다.

명령·작업 위치·준비 조건·부작용을 실제 정의에서 확인한다. 테스트가 운영 데이터·자산·프로세스에 영향을 주지 않는지 프로젝트 계약에 따라 확인한다. 실행할 수 없으면 이유와 남은 검증을 명시하고 안전하게 가능한 확인을 수행한다. 새 테스트나 도구는 의미 있는 검증 공백을 메울 때만 추가한다.

## 실패 원인 조사·수정·재검증

실패 출력과 관련 실행 경로를 확인해 구현 결함·환경/준비 문제·검증 자체 문제를 구분한다. 이 분류나 원인을 확인하지 못하면 UNKNOWN으로 남긴다. 기존 실패라고 단정할 때도 근거가 필요하다. 긴 도구 출력은 진단에 필요한 부분만 조회·표시한다. 원문 보존이 필요하면 민감정보와 저장 권한을 확인해 허용된 위치에 남긴다.

확인된 원인에 최소 수정을 적용하고 관련 검증을 재실행한다. 새로운 변경·실패·미해결 우려가 있을 때만 검증을 넓힌다. 환경·검증 코드 수정도 요구사항과 원래 검증 의미를 유지해야 한다. 실패를 숨기기 위한 제외·재시도·기준 완화는 하지 않는다.

실패·중단과 수정의 중요한 근거를 보존한다. 근거 없는 반복 실행, 원인이 불명확한 반복 실패, Scope·접근 방식의 큰 변경이 필요하면 공통 규칙의 중단·승인 경계를 따른다.

## 변경 검토와 결과 보고

최종 변경에서 목표 충족·불필요한 변경·회귀 위험·민감정보·검증 공백을 확인한다. 확인한 결함은 승인 Scope 안에서 수정하고 영향받은 검증을 수행한다. 별도 리뷰어·모델 호출·병렬 위임을 기본 요구사항으로 추가하지 않는다.

실제 변경·검증과 그 범위·실패 원인/수정·UNKNOWN·남은 사용자 결정을 보고하고 중요한 판단은 지정된 기존 기록에 남긴다. 기술 검증과 사용자 Acceptance를 구분한다. 요청된 작업 단위 이후의 Phase·인접 작업을 자동 시작하지 않는다.
