# 공통 개발 규칙

이 문서는 범용 하네스 0.1.1 기반의 2026-11-03 기준을 Project Log에 적용한 것이다. 프로젝트별 기준 문서·기록·승인 경계는 Root `AGENTS.md`, 실행 환경·검증은 Root `README.md`의 `준비와 실행`·`검증` 및 해당 문서가 연결한 Runtime pin·Manifest·Lockfile·`Makefile`을 따른다. 실행 절차는 연결된 `develop-change` Skill에 둔다.

## 요청·Scope·기존 작업

- 현재 사용자가 요청한 목표·완료 조건·필수 제약을 기준으로 작업한다. 읽기 전용 조사·리뷰·계획 요청에서 파일을 변경하지 않는다.
- 이미 승인된 Scope의 구현·필요한 검증·명확한 오류 수정은 이어서 수행한다. 불필요한 반복 승인을 요구하지 않는다. 필요한 결정이 비어 있으면 의존하지 않는 작업을 진행하고, 결과에 영향을 주는 최소 질문만 한다.
- 기존 수정·미추적 파일을 보존한다. 무관한 정리·Refactor·의존성 변경을 함께 하지 않는다. 요청된 논리적 작업 단위가 끝나면 보고하고 멈춘다.
- 실행 환경의 상위 지침 안에서 최신 명시적 사용자 요구를 기준으로 작업한다. 프로젝트별 기준 자료·Convention·명령·검증은 해당 프로젝트 지침, 공통 규칙은 작업 원칙, Skill은 수행 절차를 담당한다. 프로젝트가 지정한 기존 경로·명령을 적용하는 것 자체를 규칙 충돌로 취급하지 않는다.
- 적용 지침과 현재 사용자 요구의 충돌을 조용히 덮어쓰지 않는다. 중요한 승인 경계나 요구사항의 충돌은 영향과 선택지를 설명하고 사용자 판단을 받는다.

## 사실과 검증

- 현재 요구사항은 최신 명시적 사용자 결정과 지정된 기준 자료로 판단하고, 실제 구현·검증 상태는 Source·Test·Manifest·Lockfile과 관측으로 확인한다. 과거 기록이나 현재 구현을 현재 요구사항으로 승격시키지 않는다. 필요한 파일만 읽고 이미 유효한 조사·검증을 반복하지 않는다.
- 정확성·안전성·완료 조건을 유지하면서 필요한 근거를 확보할 수 있는 최소 충분한 방법을 선택한다. 조사·도구/모델 호출·검증·재시도·기록의 누적 실행 비용과 추가 산출물의 유지보수 부담을 함께 고려한다. 비용을 줄이기 위해 필수 검증이나 승인 경계를 생략하지 않는다.
- 사용자 확정사항·추천·잠정안·UNKNOWN과 구현·검증·반영·승인 상태를 구분한다. 결정 확정을 구현·검증 완료로 기록하지 않는다. 과거 의도·원인·성과를 현재 코드로 만들어내지 않고, 과거 결과와 이번 관측을 구분한다. 실행하지 않은 검증을 통과로 보고하지 않는다.
- 변경 위험과 범위에 맞는 기존 검증을 수행한다. 실패를 숨기거나 assertion·Fixture/Golden의 의미·요구사항을 낮춰 통과시키지 않는다. 기준 자체의 변경은 사용자 결정 대상이다.
- Mock·합성 검증과 실제 서비스·자료·품질의 검증을 구분한다. 자동 검증 성공을 사용자 Acceptance로 대신하지 않는다.

## 자율 처리와 승인 경계

- 기존 환경·도구와 Lockfile을 우선 사용한다. 명령의 실제 정의·파일 변경·네트워크·DB·프로세스 부작용을 확인한 뒤 현재 승인과 실행 권한 안에서 수행한다.
- Scope·Architecture·중요 Product/Design 결정, 주요 Dependency/Runtime 변경, 개발 대상의 Credential 사용·승인되지 않은 외부 API/AI 호출·비용·private data 전송, 운영 데이터·서비스 변경, 복구가 어려운 파괴적 작업은 실행 전에 목적·영향을 설명하고 필요한 승인을 받는다. 이미 명시적으로 승인된 범위는 재승인을 요구하지 않는다.
- 실제 작업 Repository의 Git staging/commit/push와 reset/clean/rebase/history rewrite는 명시적 승인 없이 하지 않는다. 프로젝트 검증이 소유한 임시 fixture의 허용 작업은 해당 검증 계약을 따른다.
- Secret·Credential 원문을 지침·문서·로그·산출물에 넣지 않는다. 접근 가능한 도구·권한이 행동의 사용자 승인을 뜻하지는 않는다.
- 일반적인 실패는 원인을 확인하고 최소 수정·재검증한다. 새 근거 없이 같은 실패를 반복하거나 원인이 불명확한 채 접근·Scope를 크게 바꿔야 하면, 수행 결과와 UNKNOWN·선택지를 보고하고 사용자 결정을 받는다.

## 결과와 중요한 근거

- 실제 변경, 실행한 검증의 명령·작업 위치·결과·범위, 중요한 실패·수정, 미검증 사항과 남은 결정을 간결하게 보고한다. 성공 결과를 검증하지 않은 영역으로 확대하지 않는다.
- 중요한 판단·검토한 대안과 선택 이유·실패 원인과 수정·검증 근거·결과·UNKNOWN은 프로젝트가 지정한 기존 개발 기록에 필요한 만큼 보존한다. 실제로 검토·관측한 내용만 기록하고 민감정보는 제외한다. 과거 기록을 최신 결정에 맞춰 소급 바꾸지 않고, 결정·상태가 바뀐 시점과 출처를 구분해 보완한다.
- 기록 위치가 없으면 결과 보고에 근거를 남긴다. 별도 기록 체계·대화 자동 수집 기능을 만들지 않으며, 장기 기록을 임시 진행 상태 저장소로 사용하지 않는다. 일상 작업 종료나 세션 이동만으로 상태·인수인계 파일을 만들거나 갱신하지 않는다.

## 조건부 세션 인수인계

- 실제 세션 전환·Context 유실 위험이 있고, 기존 개발 문서만으로 미완료 작업의 중요한 맥락을 충분히 복원하기 어려울 때만 최소한의 일회성 인수인계를 작성한다. 장기 개발 Evidence 보존은 인수인계 필요 여부와 별개로 계속한다.
- 임시 파일에는 작성 시점·대상 프로젝트/작업을 식별할 정보와 다음 작업·미해결 사항·승인 경계·필요한 근거 위치만 담는다. 판단·대안·실패·검증·결과·UNKNOWN의 상세는 먼저 기존 개발 기록에 보존하고 중복 복사하지 않는다.
- 필요한 경우에만 프로젝트가 지정한 Git 제외 위치에 작성하고 실제 경로를 사용자에게 알린다. 새 세션은 프로젝트 지침의 지정 위치나 사용자가 전달한 경로에서 존재·사용 완료 여부를 확인하고, 작성 시점·대상·미완료 내용을 현재 요청·Working Tree·기준 문서와 최소 대조해 관련성·최신성을 판단한다. 파일이 없으면 정상이며, 무관하거나 오래된 내용을 현재 지시로 실행하지 않는다. 판단할 수 없는 내용은 UNKNOWN으로 남긴다.
- 맥락 복원 후 장기 근거의 보존을 확인하고, 파일 수정이 허용된 범위에서 `사용 완료`로 표시해 재사용을 중단한다. 읽기 전용 요청에서는 표시도 변경하지 않는다. 삭제·교체는 프로젝트의 승인·보존 규칙을 따르고, 미완료인 다른 작업의 인수인계를 덮어쓰지 않는다.
- 이 지침은 에이전트가 확인·판단할 절차다. 세션 전환·Context 잔량의 자동 감지, 파일 자동 생성·소비·삭제 기능을 전제하지 않는다.
